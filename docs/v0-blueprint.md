# UI 质量工作台 V0 产品蓝图

状态：Draft
日期：2026-08-26

## 1. 产品定义

UI 质量工作台是一套由 AI Skill 驱动、在本地浏览器中运行的 UI 审查平台。它把设计来源、开发实现、审查规则、证据和修复清单放进同一个审查上下文中。

V0 只交付第一个完整模块：**UI 一致性走查**。架构必须允许以后增加交互体验、可访问性、响应式、设计系统合规和文案检查，但 V0 不实现这些模块。

### 1.1 V0 核心价值

当开发页面进入验收阶段时，设计师或前端可以：

1. 导入一个具体的 Figma Frame，或上传设计稿图片。
2. 上传同一页面、同一状态的实现截图。
3. 在统一视口下完成设计稿与实现图的对齐。
4. 得到带证据、置信度和建议优先级的候选问题。
5. 人工确认、忽略或调整问题。
6. 导出可以直接交给研发的修复清单。

### 1.2 产品原则

- **本地优先**：截图、分析结果和审查记录默认保存在本机。
- **证据优先**：每个问题必须绑定可定位的截图区域或结构化证据。
- **结论分层**：区分测量、观察、推断的证据来源，并另行记录人工审阅状态。
- **人机共审**：自动分析只产生候选问题，不能跳过人工确认直接成为最终结论。
- **模块共享闭环**：所有审查模块共享 Project、AuditRun、Finding、FindingOccurrence、Evidence 和 Export。
- **Skill 不承载应用本身**：Skill 负责启动和编排，本地工作台负责复杂交互与状态。

## 2. V0 范围

### 2.1 V0 Core 必须交付

- 本地工作台启动、关闭和运行状态提示。
- UI 一致性走查任务创建。
- 设计来源：图片上传。
- 实现来源：图片上传。
- 页面名称、视口宽高、DPR 和状态名称记录。
- 两图尺寸校验，以及原始像素、按宽度等比和平移微调三种有限对齐方式。
- excludedRegion 矩形屏蔽、并排、透明叠加和差异热力图。
- 确定性像素差、空间聚合和保守的问题类型建议。
- 问题确认、驳回、忽略、优先级调整和备注。
- Markdown 和 JSON 导出。
- 从创建审查开始持续自动保存；关闭并重新打开后仍可恢复输入、配置、运行和审阅结果。

### 2.2 V0 Beta，不阻塞 Core 发布

- 具体 Figma Frame URL 导入；授权或导入失败时回退到图片上传。
- 基于 Figma 可获得元数据的尺寸与来源提示。

图片上传路径必须能独立完成完整闭环，不能因为 Figma Beta 不可用而阻塞发布。

### 2.3 明确不进入 V0

- 多人实时协作、账号和权限系统。
- 云端项目同步。
- 项目、版本和发布批次管理。
- Jira、Linear、飞书等第三方任务写入。
- 开发 URL 自动截图、登录态录制和页面爬取。
- 登录态复杂页面的自动操作录制。
- 自动修改前端代码。
- DOM、computed style 和 Figma 节点的自动一一匹配。
- 自由旋转、透视或非等比图像配准。
- 按检查类型配置复杂规则集。
- PNG 报告、复制为新审查和自动清理策略。
- 在 Finding 中编辑完整验收标准。
- 完整交互体验审查。
- 第三方审查模块市场。
- 移动端原生应用。

### 2.4 V0 Beta 的 Figma 边界

V0 的 Figma URL 必须指向一个具体 Frame，并且只负责：

- 识别文件、页面和 Frame。
- 导出选定 Frame 的基准图片。
- 保存 Frame 名称、尺寸、来源链接，以及 API 可获得时的文件级或节点级更新时间。

私有文件必须先完成授权。若授权不可用，应明确提示用户改用图片上传，不能假装导入成功。节点级 Token、字体、组件和 Auto Layout 对比属于后续增强。

### 2.5 V0 的实现截图边界

V0 不负责打开或操作开发页面。用户上传实现截图时需要记录 viewport、DPR、页面状态和可选备注。系统应检查两张图的宽高比和尺寸关系；不满足可靠对比条件时，默认阻止直接分析，允许用户重新上传，或显式选择“按宽度缩放，结果可能产生误报”。

### 2.6 V0 的检测结论边界

V0 可以可靠承诺的是：在用户确认对齐后，测量像素差、聚合差异区域并保存可复查证据。问题类型和修复文案属于辅助判断：

- 首版分类限定为 `visual.geometry`、`visual.color`、`visual.typography`、`visual.asset`、`visual.missing-or-extra` 和 `visual.unknown`；
- 无法可靠分类时必须使用 `visual.unknown`，不能为了清单完整度强行猜测；
- 没有 DOM 或 Figma Node 数据时，不能声称已经测得真实 CSS 属性、Token 或组件参数；
- 外部 AI 默认关闭；每次审查首次发送前都要显示发送范围并取得明确授权；用户拒绝后，基础差异检测、人工审阅和导出仍需完整可用。

## 3. 信息架构

```text
UI 质量工作台
├── 首页
│   ├── UI 一致性走查入口
│   └── 最近审查
├── 新建审查
├── 审查工作区
├── 审查记录
└── 设置
    ├── Figma 连接
    ├── 本地存储
    └── 隐私与数据发送
```

V0 可以只显示已安装的 UI 一致性走查模块。不要用大量“即将上线”卡片伪装工作台规模。

## 4. 主用户流程

```text
通过 Skill/CLI 启动，或在服务已运行时打开本地地址
                ↓
          新建 UI 走查
                ↓
        创建记录并开始自动保存
                ↓
   导入设计来源 + 导入实现来源
                ↓
    记录视口、状态和 excludedRegion
                ↓
       预览并确认两图对齐关系
                ↓
             开始分析
                ↓
       人工确认候选 Finding
                ↓
        持续保存，可按需导出清单
```

## 5. 页面结构

### 5.1 首页

目标：尽量减少开始一次走查或继续最近记录所需的步骤。

主要区域：

- 顶部：产品名称、本地运行状态、设置入口。
- 主操作：开始 UI 一致性走查。
- 最近走查：来源、目标、运行状态和结果摘要。

关键状态：

- 首次使用：解释本地存储和第一步，不展示空数据表格。
- 无 Figma 授权：只有使用 Figma 时才提示连接。
- 本地服务异常：显示可执行的恢复动作，而不是通用错误。

### 5.2 新建走查向导

#### 步骤一：设计来源

- Figma Frame URL。
- 本地图片上传。
- Frame 或图片预览。
- 显示来源尺寸，阻止无法读取的假成功状态。

#### 步骤二：实现来源

- 本地截图上传。
- 记录页面或状态名称、viewport 和 DPR。
- 显示截图尺寸，阻止空文件、异常格式和无法解码的输入。

#### 步骤三：对齐与规则

- 显示设计稿和实现图尺寸。
- 选择原始像素、按宽度等比或平移微调。
- 可新增 excludedRegion 并说明原因。
- V0 使用固定基础规则，不提供复杂检查类型配置。

#### 步骤四：运行确认

- 汇总输入、环境和规则。
- 明确哪些信息是直接获取，哪些是推断。
- 启动分析。

### 5.3 走查工作区

布局参考 Yangao 的“双图对比 + 问题列表”任务模型，并增加证据分级和人工审查能力：

```text
┌──────────────────────────────────────────────────────────────┐
│ 走查名称             运行状态     重新分析      导出          │
├───────────────────────────────────────────┬──────────────────┤
│ 标注 | 并排 | 叠加 | 热力图    缩放/对齐  │ 问题清单与筛选   │
│                                           │ 严重度 / 优先级  │
│                                           │ 类型 / 审查状态  │
│                 对比画布                  │                  │
│                                           │ Finding cards    │
│                                           │                  │
├───────────────────────────────────────────┴──────────────────┤
│ 选中问题详情：证据、预期、实际、置信度、状态、备注             │
└──────────────────────────────────────────────────────────────┘
```

右侧每个 Finding 必须支持：

- 聚焦画布位置；
- 查看设计、实现和差异证据；
- 确认或驳回；
- 设置忽略原因；
- 调整 priority；
- 添加面向开发的备注。

### 5.4 导出弹窗

目标：让导出前的范围可审阅，而不是点击后直接下载不可控文件。

主要区域：

- 已确认问题统计和优先级摘要。
- 是否包含未确认问题的显式选项。
- Markdown、JSON 导出。

默认只导出已确认的问题；候选问题只有用户主动选择时才能进入报告。导出按 P0 → P3 分组，`priority=unset` 单独放在“待定优先级”，不能静默塞进 P3。

### 5.5 审查记录

- 审查名称、时间和状态。
- 两个输入缩略图和来源信息。
- 候选、已确认和已忽略数量。
- 打开已有记录。

### 5.6 设置

- Figma 连接和撤销。
- 本地空间占用和删除入口。
- 是否允许将截图或裁剪区域发送给外部 AI。
- 引擎版本与诊断信息。

## 6. 关键状态设计

不能把输入、运行和审阅状态塞进同一个枚举。V0 使用三组正交状态：

`inputState`：

- empty：尚无输入；
- importing：正在读取上传或 Figma 来源；
- invalid：授权、Frame、图片或尺寸异常；
- ready：输入齐全并已确认对齐。

`runStatus`：

- draft：审查已创建但尚未运行；
- queued：等待引擎；
- running：正在分析，可显示真实阶段但不能伪造百分比；
- completed：运行完成；
- failed：保留输入和配置，可从失败阶段重试；
- cancelled：用户请求取消，保留诊断信息；
- stale：结果产生后，输入、对齐、excludedRegion 或分析配置发生变化。

`triageStatus` 是 AuditRun 的聚合摘要：

- not-applicable：运行未完成，或没有候选；
- needs-review：至少有一个 pending Occurrence；
- triaged：所有候选都已 confirmed、dismissed 或 ignored。

“无差异”和“有候选”是 result summary，不是 runStatus。stale 结果默认禁止导出，必须重新运行；每次状态变化都持续自动保存。

## 7. Finding 审查规则

### 7.1 严重度与优先级必须分开

- `severity`：问题本身对视觉或体验的影响程度，由审查模块建议。
- `priority`：团队处理顺序，需要结合页面任务、元素重要性和发布日期。
- `confidence`：当前判断有多可靠。

不能因为差异面积大就直接给出 P0。缺乏业务上下文时，priority 保持 `unset` 或给出可修改的建议值；V0 禁止引擎自动落盘 P0，必须由人确认。

### 7.2 证据等级

- `measured`：从 Figma 节点、DOM、computed style 或确定性测量得到。
- `observed`：截图中可直接观察，但无法得到真实属性值。
- `inferred`：通过视觉算法或 AI 推断。

人工确认不是一种证据等级，而是独立的 `reviewStatus`。用户确认一个推断结论后，它仍然是“已确认的推断”，不能被改写成测量事实。界面和导出中必须同时显示证据等级与审阅状态。

### 7.3 Finding 与 Occurrence

界面中的一张问题卡看起来是一个 Finding，但数据层仍拆成两部分：

- `Finding`：问题身份、当前严重度和处理优先级；数据结构允许以后跨多次审查关联；
- `FindingOccurrence`：某次 AuditRun 观察到这个问题时的坐标、证据、置信度、测量值和人工审阅结果。

V0 不实现自动跨运行匹配：每个候选创建一个新的 Finding，与 Occurrence 保持 1:1，只保存 `fingerprintCandidate` 供后续研究。不能仅凭截图坐标宣称两次运行中的问题是同一个。拆分两层只是避免以后复测时覆盖旧证据。

V0 只需要支持 Occurrence 的审阅状态：

- `reviewStatus`: pending / confirmed / dismissed / ignored
- `resolutionStatus` 在 V0 固定为 `not-applicable`；
- `verificationStatus` 在 V0 固定为 `not-requested`；两者只为后续修复与复测预留。

后续复测才启用完整闭环：

```text
FindingOccurrence: pending ─┬─→ confirmed
                            ├─→ dismissed
                            └─→ ignored

resolutionStatus: open → fixed
                      └→ reopened

verificationStatus: not-requested → pending → passed / failed
```

### 7.4 三种“忽略”必须区分

- `excludedRegion`：分析前屏蔽动态时间、广告或隐私区域，不生成候选；
- `dismissed`：候选是误报，实际问题不成立；
- `ignored`：差异真实存在，但当前这次审查决定不纳入修复清单，必须填写原因。

V0 的 ignored 只作用于当前 Occurrence。跨运行持久抑制和 `wont-fix` 属于后续能力，不能暗中复用 ignored 实现。

## 8. 成功指标

V0 上线后优先观察：

- 候选问题人工确认率；
- 误报率及主要误报类型；
- 从导入到第一份可用清单的时间；
- 每次走查完成 triage 的比例；
- 设计图上传、实现图上传和 Figma 导入各自的成功率。

“检测出的问题数量”不能单独作为成功指标，否则会激励系统制造噪音。

## 9. V0 验收标准

Core 完成需要以下场景全部通过：

1. **主路径**：用户通过 Skill 启动工作台，上传设计图和同一状态的实现截图，记录 viewport/DPR，确认对齐与 excludedRegion，得到候选，驳回一个误报、确认一个问题、调整 priority，并导出只含 confirmed 项的 Markdown 与 JSON。
2. **已知差异样例**：一组固定双图包含已知位置、尺寸和颜色差异；系统生成可定位 Evidence，不能只输出无坐标的自然语言清单。
3. **无差异样例**：相同图片得到 completed + no-differences，不制造候选噪音。
4. **尺寸异常**：宽高比或视口不可靠时默认阻止运行；用户显式选择按宽度等比后，报告显示误报风险。
5. **失败恢复**：图片解码或分析失败后保留输入、配置和错误阶段，修正后可以重试。
6. **持续保存**：在未导出的情况下关闭浏览器并重启 Daemon，仍能恢复审查记录和人工 reviewStatus。
7. **隐私降级**：拒绝外部 AI 数据发送后，像素差、人工审阅和导出仍能完成。

Figma Beta 升级为稳定能力前，另需通过：

1. 具体且有权限的 Figma Frame 可以导入为基准图；
2. URL 没有指定 Frame 时返回明确错误；
3. 无权限、授权撤销或网络失败时不生成假预览，并可无损切换为图片上传。
