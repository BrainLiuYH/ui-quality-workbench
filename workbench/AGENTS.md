# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

## Confirmed visual direction

- The platform's user-facing name is “设计工具箱” (Design Toolbox), covering UI inspection and the collection of useful tools and Skills. Keep the existing `ui-quality-workbench` repository, Skill identifier, and storage keys for compatibility; use the platform name in the header, browser title, installation display metadata, and current documentation.
- The user selected the third ideation option on 2026-08-26.
- Preserve its audit-session workbench structure: compact left navigation, comparison evidence above a findings table, and a persistent right-side decision inspector.
- On 2026-08-26 the user approved the refined Fluent + Ant direction shown in `../design-previews/selected-fluent-ant-direction.png`; this supersedes the earlier grayscale-only styling.
- Use a light blue-gray application shell, white working surfaces, cobalt-blue active and primary states, compact enterprise density, 8–10px control radii, 10px panel radii, fine cool-gray borders, and restrained low elevation. Keep amber limited to Beta/warning semantics.
- Local image input must support both click-to-select and single-file drag-and-drop. The main empty design/implementation placeholders and the matching zones in the upload dialog should visibly highlight during a valid file drag while keeping each role unambiguous.
- In side-by-side mode, design and implementation must live in one keyboard-accessible shared scroll region so vertical and horizontal movement always keeps them together. Other single-image comparison modes may retain their own scroll region. Tall content must remain reachable from top to bottom at every supported zoom level without clipping transformed content.
- Each populated design/implementation pane must expose explicit, role-specific replace and remove actions. Replacing or removing either input must cancel stale imports, release the old object URL, clear stale findings, and preserve the other input.
- The default audit/session title must be derived from the imported filenames or source metadata and shown consistently in the toolbar, history item, and exports. Never reuse prototype-only page names; once the user manually renames a session, later input changes must preserve that name.
- Before raster comparison, explicitly distinguish different export scales from different responsive viewport widths. For same-pixel-density responsive captures, retain each screenshot at 1× and compare only their shared viewport area; when export scales differ, keep the wider image at 1× and proportionally enlarge only the narrower image to that width. The mobile-width heuristic is only a default guess, not proof of identical DPR: expose a switch and label the assumption clearly. Top-left alignment remains the default, with an explicit bottom-left mode for audits anchored to the page bottom. Changing alignment or scale mode must invalidate stale results and rerun the engine in the same coordinate space used by preview, annotations, evidence crops, and exports. Preserve unmatched height as comparison evidence when the screenshots represent the same viewport; do not classify extra responsive viewport area as missing UI. Never non-uniformly stretch either source.
- Expose a manual element-alignment workflow for screenshots that do not share a reliable page edge: the user first frames a stable element in the design and then the corresponding element in the implementation. Apply center-to-center X/Y translation only after explicit confirmation; never infer scale from the two boxes. Analyze only the overlapping image area, keep selection coordinates image-local, and use the same placements for preview, findings, evidence crops, and exports.
- Before classifying local differences, run an input-comparability gate on the normalized rasters. Low-comparability pairs must stop without generating a misleading issue list; medium-comparability pairs may continue only with a persistent human-review warning. Never present the gate score as a calibrated probability.
- Treat matching page geometry with different placeholder text, media, or business data as reviewable. Widespread content variation may lower comparability to medium and require human review, but it must not become low solely from pixel, colour, or fine-content divergence; reserve blocking for strong evidence of incompatible viewport or coarse layout structure.
- Content-only changes, small single-sided contours, and compact regions without positive semantic evidence are review-only observations: summarize them in the comparability warning, but do not turn them into list rows or canvas annotations. A large, internally textured region that is nearly flat/blank on the other side can be an actionable *presence question*, provided the UI explicitly asks for state/content confirmation; do not turn that observation into a confirmed layout or CSS defect. Size, position, and layout findings require usable contour evidence on both sides.
- The bottom findings list must be collapsible without losing its filter or selection state, and collapsing it must give the released height back to the comparison canvas. Every visible row action must perform a clear operation; never ship inert icon buttons, sort indicators, checkboxes, or pagination controls.
- Default findings copy must use short, plain Chinese: describe what looks different, its approximate page area, and the visible reason. Keep coordinates, pixel heuristics, edge density, confidence signals, and other engine terms out of the default list and detail panel; retain them only as hidden technical metadata.
- Treat one-sided transparent pixels as a single region-presence/layout candidate. Transparent RGB bytes are not black content and must not generate color, text, icon, border, shadow, or size claims.
- Require positive raster evidence before assigning text, icon, or media roles. Use neutral names for ambiguous or slender fragments, keep localized media/content changes separate from UI geometry claims, and prefer one primary objective classification per visual object over several contradictory types.
- Treat component spacing, absent-versus-present borders, fill treatment, corner shape, and selected-state styling as first-class regression cases. A responsive comparison must preserve these local signals even when screenshots use different viewport widths; do not let global width normalization, changing media behind a translucent component, or single-label candidate selection hide a visible difference. Keep one annotation per visual component, but retain independently evidenced color and structural sub-issues inside that group. This requirement was reinforced by the user's 2026-09-16 report covering the draft-entry relationship, online-status chip treatment, and bottom navigation outline/corners/selection.
- The user does not want the upstream Yangao Skill to define product judgments. Use the workbench-owned classification and evidence contract in `skill-package/references/audit-classification.md` as the source of truth: keep category separate from severity and priority, preserve underlying evidence types, allow manual recategorization, and do not use a universal 1px mismatch threshold.
- Treat the user's ongoing correction of missed/incorrect findings as a maintained regression corpus, not as permission to hardcode one screenshot. Before changing detection, update `skill-package/references/audit-feedback-cases.md` with the observation, evidence limits, counterexample, and current support status. New automatic rules need a positive and a negative regression test, plus a real-pair check when those inputs remain available. A larger rule count is not proof of higher accuracy: watch both false negatives and false positives, and keep unsupported typography, blur/CSS, dynamic-content, and corner-radius claims explicitly open for human review.
- Keep a first-class “工具分享” entry in the left navigation. It is a curated collection of useful tools and Skills, not another audit mode: show the collection as clickable cards, open a plain-language detail dialog from each card, and preserve all UI-audit state when switching between the two views. The first confirmed entries are Cowart (label it accurately as a tool plugin containing multiple Skills) and the `ui-wireframe-workflow` mobile low-fidelity prototyping Skill.
- Each shared tool must offer “一键安装” on its card and detail dialog. This opens a copyable installation prompt with clear instructions to paste and send it to an AI tool that supports the required installation. Prompts must be portable: use a verified public source or include all required Skill files, never a sharer's local address or a fabricated download link. Show truthful copy success or a manual-copy fallback, and label collection status independently of the visitor's installation status.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.
